关键发现：caelus 不会被八字/紫微拉入

  • caelus 的 47MB 全部是天文星历原始数据（vsop87d_*.embedded.json 等），只被 西方星盘 / 月相天文 模块引用。
  • mingyu-core/dist/bazi/ 目录 零引用 caelus（已 grep 验证）。
  • caelus 与 mingyu-core 均声明 sideEffects: false → 打包时 tree-shaking 可剔除未用分支。
即：只用一个 mingyu-core/bazi 子入口，前端实际增量远小于「全量 76MB 安装体积」给人的印象。但需实测最终 bundle 大小确认。

五、技术接入注意点

  • ESM-only：mingyu-core 的 exports 只提供 import，无 CJS require。现状项目是传统 <script> 全局脚本，必须走打包器（Vite/esbuild）或改用 ESM，不能像 lunar.js 那样直接 <script src> 引入。
  • 紫微需注入 iztro：mingyu-core 把 iztro 作为 optional peerDependency，其 resolveIztroAstro 在纯 Node 下找不到 iztro；实际调用需按其 runtime 契约注入。
  • 输入契约：八字用 {year,month,day,timeIndex,gender}（timeIndex 0=早子…11=亥，12=晚子），与我们现有 select 值可映射。
  • 许可：AGPL-3.0-only。已确认你接受开源 → 前端整站以 AGPL 开源即可合规。

六、建议

值得做的
  • 用命语补齐八字深度：格局 / 用神 / 神煞 / 调候 / 精确大运
  • 只用 mingyu-core/bazi 子入口，避免全量依赖
  • 先做一次 Vite 打包体积实测再决定
不建议
  • 替换紫微（同源 iztro，零收益）
  • 引入全量 packages（含西占星盘 47MB caelus）
  • 长期深度绑定（作者业余维护，bus factor = 1）
长期看，既已接受开源，可将命语作为能力参考与交叉验证基准，关键排盘能力逐步自研固化。
